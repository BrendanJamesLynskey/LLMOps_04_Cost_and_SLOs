Token Cost Economics — Input vs Output, Cached, Batched

LLM cost is not a flat rate per request. It is the sum of token counts at different prices depending on the token’s origin and processing mode. Modelling this correctly is the foundation of every cost metric.

Token categorygpt-4o (Apr 2025)claude-3-5-sonnet (Apr 2025)Key point
Input (uncached)$2.50 / M tok$3.00 / M tokStandard rate; baseline for all comparisons
Input (cached read)$1.25 / M tok$0.30 / M tok50% and 90% discount respectively
Cache write (Anthropic only)—$3.75 / M tok1.25× write penalty; amortised over reads
Output$10.00 / M tok$15.00 / M tok4× input price; output volume dominates cost
Batch input$1.25 / M tok$1.50 / M tok50% off; ≥24 h turnaround; not for interactive
Batch output$5.00 / M tok$7.50 / M tok50% off output too; significant for heavy generation

Cost formula

Per-request cost model

cost = (input_uncached × p_in) + (input_cached_write × p_write) + (input_cached_read × p_read) + (output × p_out)

For a typical support-bot request with a 4 K-token system prompt (cached after first call), 500-token user message, and 300-token response on gpt-4o: write call = (4000 × $2.50 + 500 × $2.50 + 300 × $10.00) / 1e6 = $0.014. Subsequent reads = (4000 × $1.25 + 500 × $2.50 + 300 × $10.00) / 1e6 = $0.009. Cache saves 36% per call after warm-up.

Throughput vs Latency — TTFT, TPS, p95 Token-Out

LLM latency has a two-phase structure that is fundamentally different from a conventional HTTP call. Measuring only total duration misses the part that users feel most.

MetricDefinitionTypical values (gpt-4o, 2025)SLO relevance
TTFTWall-clock from request sent to first token received300–800 ms uncached; 100–300 ms cached prefixCritical for interactive UX; users feel >500 ms
TPS (output)Output tokens / decode duration40–80 tok/s for 4o; 20–40 for Opus 3Reading speed comfort ≈ 30 tok/s (≈ 150 wpm)
p95 E2E95th-percentile total duration over 1-hour window4–12 s for 300-token outputHard SLO ceiling; alerts if exceeded
Throughput (RPS)Completed requests / second at the gatewayLimited by provider TPM quotaCapacity planning, not user-visible
Measure TTFT, not just E2E

E2E latency conflates the two phases. A 10-second response with TTFT of 200 ms feels fast because the user sees the stream starting immediately. A 3-second response with TTFT of 2.9 s feels slow. Set separate SLOs: TTFT p95 ≤ 600 ms; TPS floor ≥ 25 tok/s. Use your gateway’s span start & first-chunk timestamps to compute these separately.

03

Per-Task Cost Metric — Cost-per-Resolved-Ticket

Raw token costs are meaningless without a business denominator. The right unit depends on the application, but the pattern is always the same: sum all LLM costs for a workflow and divide by the unit of business value delivered.

Support bot

Metric: cost per resolved ticket
Formula: Σ (token costs across all LLM calls in the session) / (sessions that ended in resolution)
Typical target: <$0.05 / resolved ticket

Code review bot

Metric: cost per PR reviewed
Formula: Σ (diff analysis + comment generation costs) / PRs reviewed
Typical target: <$0.20 / PR (scales with diff size)

Document summariser

Metric: cost per page summarised
Formula: total monthly LLM cost / total pages processed
Typical target: <$0.002 / page (at 500 tokens/page, Sonnet 3.5)

Computing cost-per-resolved-ticket from a Langfuse trace export
import pandas as pd

df = pd.read_csv("langfuse_traces_2025-04.csv")

# token_cost_usd already computed by Langfuse using its price table
session_cost = (
    df.groupby("session_id")
    .agg(total_cost=("token_cost_usd", "sum"),
         resolved=("session_resolved", "max"))
    .reset_index()
)

resolved_only   = session_cost[session_cost["resolved"] == 1]
cost_per_ticket = resolved_only["total_cost"].mean()

print(f"Cost per resolved ticket: ${cost_per_ticket:.4f}")
print(f"p95 session cost: ${resolved_only['total_cost'].quantile(0.95):.4f}")
Track the denominator too

Cost-per-ticket can improve because the bot resolves more tickets (good) or because it deflects customers who then call the phone line (bad). Always track both the per-task cost and the task completion rate together. A model change that halves cost but drops resolution rate by 30% is a net loss.

04

Capacity Planning — Concurrency, Queue Depth

Provider rate limits are measured in two orthogonal dimensions: requests per minute (RPM) and tokens per minute (TPM). Your capacity model must account for both, because hitting either limit degrades throughput.

Key relationships

Little’s Law applied to LLMs

L = λ × W, where:
L = concurrent in-flight requests
λ = request arrival rate (req/s)
W = mean response latency (s)

At 20 req/s with 5 s mean latency: L = 100 concurrent requests. If your provider allows 50 concurrent connections, you need queuing.

TPM saturation

For gpt-4o Tier 4: 800 K TPM. At 2000 tokens/request average: 400 req/min maximum. At p95 latency of 6 s: concurrent in-flight = 400/60 × 6 = 40 concurrent requests. Buffer 20% for bursts → size your connection pool at 48.

Queue depth and backpressure

Queue depthSignalAction
0–10% of burst capacityHealthyNone; monitor
10–50%Elevated loadAlert on-call; check if a provider is degraded
50–80%Approaching limitShed low-priority traffic; enable fallback to secondary model
>80%SaturationReturn 503 to new requests; preserve capacity for in-flight SLA-bound requests
Streaming and concurrency

Streaming responses hold a connection open for the full token-generation duration. A 300-token response at 50 tok/s = 6 seconds of held connection. With 100 concurrent streaming requests you need 100 persistent connections to the provider. Account for streaming in your connection pool sizing — it is typically 5–10× larger than for synchronous requests at equivalent RPS.

Rate Limiting — Token Bucket, Fairness Across Tenants

Rate limiting at the gateway protects both your provider quota and individual tenants from each other. Token bucket is the standard algorithm; it naturally handles bursty LLM traffic.

Token bucket mechanics

Bucket capacity = B tokens
→
Refill rate = R tokens/s
→
Request arrives: costs C tokens
→
if bucket ≥ C: admit & deduct
→
else: 429 + Retry-After: (C-bucket)/R
Redis-based token bucket (sliding window, Lua atomic)
-- Key: "rl:{tenant_id}"
-- ARGV: request_tokens, bucket_capacity, refill_rate, now_ms
local key = KEYS[1]
local cost, cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]),
                               tonumber(ARGV[3]), tonumber(ARGV[4])

local vals = redis.call("HMGET", key, "tokens", "ts")
local tokens = tonumber(vals[1]) or cap
local ts     = tonumber(vals[2]) or now

local elapsed = (now - ts) / 1000        -- seconds
tokens = math.min(cap, tokens + elapsed * rate)

if tokens < cost then
    return {0, math.ceil((cost - tokens) / rate * 1000)}  -- {denied, retry_ms}
end
redis.call("HMSET", key, "tokens", tokens - cost, "ts", now)
redis.call("PEXPIRE", key, math.ceil(cap / rate * 1000))
return {1, 0}                                            -- {admitted, 0}
Fairness: limit by output tokens, not requests

Limiting by request count is unfair: one tenant asking for 4096-token responses consumes the same quota slot as another asking for 50-token responses. Deduct estimated output tokens from the bucket at admission (estimate = min(max_tokens, 256)). Update the bucket with the actual token count on response. This is the approach used by LiteLLM’s max_tpm per-key enforcement.

SLO Design — Availability, Quality, Latency

LLM SLOs must cover three dimensions that traditional services rarely track together. Define each independently with a separate error budget.

SLO dimensionDefinitionExample targetMeasurement
AvailabilityFraction of requests that return a valid non-error response99.5% / 30-day rolling windowhttp_requests_total{status!="5xx"} / http_requests_total
Latency (TTFT)p95 TTFT ≤ target across 1-hour windows600 ms p95Gateway span first-chunk timestamp minus request-received timestamp
Latency (E2E)p99 E2E ≤ target for >95% of 1-hour windows15 s p99Gateway span end minus start
QualityFraction of responses scoring above eval threshold≥85% score ≥0.7 on automated evalLLM-as-judge sampled at 5%; alert on 7-day rolling drop
Finish reasonFraction of responses finishing with stop (not length or content_filter)≥97% stop reasonGateway response parser; alert on >3% non-stop

Error budget algebra

30-day error budget

At 99.5% availability: budget = 30 × 24 × 60 × 0.005 = 216 minutes of allowed downtime. Burn rate alert: if you’re consuming the budget 2× faster than the 30-day window allows (i.e. burn rate > 2), alert the team even if you’re still within budget. This gives lead time to investigate before the budget exhausts. Quality SLO uses the same algebra: 85% quality with 5% sampling rate means 0.15 × 5% = 0.75% of all requests can be bad — set your alert at 0.5% to leave headroom.

Budget Enforcement — Alerts, Hard Limits, Chargeback

Uncontrolled LLM spend is one of the fastest ways to create a CFO incident. Budget enforcement must be automated — manual review of invoices is too slow when a runaway agent loop can spend $10 K in an hour.

Soft alerts (warn)

  • Trigger at 50% and 80% of monthly budget
  • Send Slack alert to team channel
  • Log to PagerDuty at 80%
  • Include breakdown: top-3 cost-by-team, top-3 cost-by-model
  • No traffic impact; informational only

Hard limits (enforce)

  • At 95%: disable all non-SLA-bound traffic (background jobs, batch)
  • At 100%: gateway returns 429 for new requests from over-budget tenants
  • Exempt: production interactive traffic on SLA contracts
  • LiteLLM: max_budget + budget_duration per virtual key

Chargeback

  • Tag every request with team, product, environment at the gateway
  • Export hourly cost roll-ups to your internal BI (BigQuery / Redshift)
  • Allocate actual provider invoice proportionally to usage tags
  • Monthly: each team receives their LLM cost allocation for P&L reporting
Prometheus alerting rule — LLM spend burn rate
groups:
  - name: llm_budget
    rules:
      - alert: LLMBudgetBurnRateHigh
        expr: |
          rate(llm_cost_usd_total[1h]) * 730 > 0.8 * llm_monthly_budget_usd
        for: 10m
        labels: {severity: warning}
        annotations:
          summary: "LLM spend burn rate will exhaust monthly budget"
          description: "Projected monthly spend: {{ $value | humanizeCurrency }}"

Forecasting — Usage Growth, Model-Cost Falls

LLM cost forecasting has two competing trends that make it non-trivial: usage typically grows super-linearly with product adoption, but model prices fall — often 50–80% year-over-year. A good forecast models both.

Historical model price evolution (input tokens, $/M)

Model generationFlagship price (launch)12 months laterΔ
GPT-4 (2023-03)$30.00 / M input$10.00 / M input−67%
GPT-4-turbo (2023-11)$10.00 / M input$2.50 / M input (gpt-4o)−75%
Claude 3 Opus (2024-03)$15.00 / M input$3.00 / M input (Sonnet 3.5)−80%
GPT-4o (2024-05)$5.00 / M input$2.50 / M input−50%

Forecast model

Python — simple LLM cost forecast with usage growth + price decay
import numpy as np

monthly_tokens_now = 500_000_000       # 500M tokens / month today
price_per_m_now    = 2.50              # $/M input tokens (blended)
monthly_growth     = 0.15              # 15% month-over-month usage growth
annual_price_decay = 0.60              # prices fall 60% per year → 0.4× remaining
monthly_price_decay = annual_price_decay ** (1/12)

months = np.arange(1, 13)
tokens = monthly_tokens_now * (1 + monthly_growth) ** months
prices = price_per_m_now * monthly_price_decay ** months
costs  = tokens / 1e6 * prices

for m, tok, p, c in zip(months, tokens, prices, costs):
    print(f"Month {m:2d}: {tok/1e9:.2f}B tokens, ${p:.2f}/M → ${c:,.0f}/mo")
Planning implication

Typical result: usage grows from 500 M to 2.2 B tokens over 12 months, but price per million falls from $2.50 to $1.25. Monthly cost increases from $1 250 to $2 750 — 2.2× growth despite 2× usage growth — because the price decay partially offsets the volume growth. Commit to reserved capacity only when token volumes are stable and predictable; keep the majority on pay-as-you-go while in high-growth phase.

What to Take Away

  • Cost = Σ token categories × rate. Track cached-write, cached-read, uncached input, and output separately. Output tokens cost 4× input — minimise unnecessary generation length.
  • Measure TTFT and TPS separately from E2E latency. Users feel TTFT; set a 600 ms p95 TTFT SLO independently from a 15 s p99 E2E SLO.
  • Per-task cost (cost-per-resolved-ticket) is the metric that matters to the business. Track it alongside task completion rate — a cheaper model that resolves fewer tickets can be a net loss.
  • Little’s Law: L = λW. At 20 req/s and 5 s latency you need 100 concurrent connections. Size your provider connection pool accordingly, ×1.2 for burst.
  • Token bucket for rate limiting. Deduct estimated output tokens at admission; correct on response. Lua atomic in Redis. Return Retry-After calculated from bucket refill rate.
  • Three SLO axes: availability (≥99.5%), latency (TTFT p95 + E2E p99), quality (≥85% on sampled eval). Separate error budgets for each.
  • Budget enforcement: alert at 50%/80%, hard-cut non-SLA traffic at 95%, full 429 at 100%. Chargeback by team tag via gateway metadata.
  • Forecast both curves: usage grows 15%+ MoM; prices fall ~60%/year. Use pay-as-you-go during high-growth; commit reserved capacity only when volumes stabilise.
